## 2. 見直しで判明した点

| ID | 問題・根拠 | 今回の決定/着手時の対応 |
|---|---|---|

| D05 | FS-27は通常モードの最初の結合点だが、後続FS-38が段階的解答の閲覧を実装する | FS-27は完成済みの通常結果を最小レイアウトで読む。FS-38は到着順不同・未完了混在・閲覧位置保持を追加 |
| D06 | M0の実機待ちをすべての机上作業の待ち条件にすると準備が止まる | データ、契約、時計注入、純粋ロジック、fake backendの準備は先に進められる。実SDKの採用決定はM0まで保留 |

| D09 | 音声と紙面の関係は撮影時刻だけでは決まらない。端末の単調時計にも共通の原点はない | 問題内容と全体文脈で対応する。録音サンプル位置はグラスの同一boot内で扱う。異なる端末の時刻を直接引き算しない |

| D11 | モバイル通信が速くてもBluetoothの画像待ち行列は解消しない | §9の帯域式で入力の増加率を確認。圧縮・解像度・再送単位は品質と一緒に評価 |
| D12 | 取り直し後に古いAI応答が来る、閲覧終了後に残りの答えが来る | session/入力digest/結果版/閉鎖状態を照合し、古い答えで画面を開き直さない |
| D13 | 新しい1枚を取り直す操作と、以前確定したページを置き換える操作では復旧規則が違う | 新規未確定版は送信禁止。確定版の置換は新しい版が保存成功するまで旧版を保全。変更後は影響する解答を無効化 |
| D14 | グラスを折る、スマホがforce-stopされる等では、サービスを追加しただけで復帰を保証できない | 起動・切断・プロセス死を分け、前提状態を試験票に残す。M0が不成立ならスマホ操作0回を達成済みにしない |

## 3. 採用案と比較案

| 項目 | 基本案 | 比較・条件付きの案 | 判断点 |
|---|---|---|---|
| ページ検知 | 低解像度YUVの輪郭/追跡＋画質/静止判定 | 小型の紙面検出モデル | 白い机・冊子・反射での欠け検出とRAM。単純判定で十分なら依存を増やさない |
| カメラ寿命 | 解析・静止画を使い、レビュー中は撮影停止 | session保持と再構成の比較 | 3秒表示・録音連続性・再開コスト・LEDを実測 |
| 録音 | グラスAudioRecordの連続入力＋小分け保存 | SDKの音声stream | 二重にマイクを開かない。切断時も原音が残る経路を選ぶ |
| 端末間転送 | Bluetooth/CXRでチャンク送信 | 許容帯域内の圧縮と必要領域の追加送信 | グラスWi-Fiなしで実証。テザリングは今回の回避策にしない |
| AI | スマホから公式の管理サービスへ画像＋音声入力 | スマホ内ASRで先行認識、端末内推論、標準AI公式連携 | 入力と構造化結果のアプリ返却、認証、利用枠、精度。画面が開くことだけでは不十分 |
| 長い音声 | 区間認識＋全文脈整理＋問題別の画像/原音 | 大きい媒体を扱える別の公式経路 | 要約だけで否定・数字・訂正を失わない。範囲不足なら広げる |
| 解答表示 | 完成した答えを全文保存し、表示時に分割 | 数式/表の専用レイアウト | 文字数上限で切らない。未完成の生成途中を完成解答にしない |

実装例・公式パターンから使える部分:
- [RokidGlassesAppCenter](https://github.com/TakanariShimbo/RokidGlassesAppCenter):
  CUSTOMAPP/CustomCMDの要求・応答を調べる参照例。少量の制御メッセージの例を写真・録音の帯域保証へ広げない。
- [Android camera2複数ストリーム](https://developer.android.com/media/camera/camera2/multiple-camera-streams-simultaneously):
  解析と静止画を構成する設計資料。今回の機種の同時録音は別の実測項目。
- [Firebase AI Logic](https://firebase.google.com/docs/ai-logic):
  Androidから画像/音声を渡す管理サービスが第一評価候補。
  [要求制限](https://firebase.google.com/docs/ai-logic/input-file-requirements)と
  [App Checkの配布条件](https://firebase.google.com/docs/app-check/android/play-integrity-provider)を満たす必要がある。
- [whisper.cppのAndroid例](https://github.com/ggml-org/whisper.cpp/tree/master/examples/whisper.android):
  非APIの音声認識を比較する候補。対象F-51Fの精度・電池・熱は未評価。

一次資料は詳細計画作成時に取得した2026-09-06の証拠を再利用している。
モデル名や未確認のSDK呼出順をここで新たな確定仕様にはしない。

S17の具体的な遷移:
~~~text
画像P08を表示（録音中）
  → 第1ダブルタップ: capture=FINISH_PENDING、audio=RECORDING
  → 別の第2ダブルタップ: capture=FINISH_PENDING、audio=FINALIZING→ENDED
  → 単タップで取り直し: capture=RETAKE、audio=ENDEDのまま
  → P08新改訂を撮影・3秒確認
  → 撮影終了: 両manifestが揃った後に解析
~~~

S17では再び音声が必要になった場合だけ、グラス上で「録音を追加」を明示的に選ぶ。
初期実装で音声追加に未対応なら、その機能があるかのように表示しない。
録音が終了済みでも資料の訂正はできる状態モデルにする。

## 5. 資料＋読み上げの例と採点

すべて今回作成した合成問題。既存試験や利用者の録音を転載していない。
ケースのinputだけを推論入力へ渡し、expected、rubric、正解の対応表は評価側に留める。
この小さいセットは結合確認用であり、正答率95%の達成判定には使わない。

| L06 | 必要な録音がない | 材料不足を表示 |
| L07 | 終了直前の発話で条件が変わる | Q1: 36 cm² |

### 同じ資料で答えが変わる例: L01A/L01B

紙面にはA便8:10・1,200円、B便8:35・1,400円、C便9:10・1,000円と、
「放送の条件を満たす最も早い便を答える」という設問がある。

- 音声A: 出発は8:20以降9:00まで、予算1,500円以内 → B便。
- 音声B: 出発は8:50以降9:30まで、同じ予算 → C便。
- 画像だけ・音声だけ・音声を差し替えた入力を比較する。紙面と音声の両方が必要。
- 同じ答えを返した場合、音声無視/対応誤り/キャッシュキー不足を調べる。

### 訂正の例: L02

紙面は1個120円。音声は「15個です。訂正します。50個に変更してください」。
答えは6,000円。初期の数量だけで1,800円と答える、要約で訂正を落とす、という失敗を検出する。

### 長文の例: N04

111文字の参照証明と4点の採点基準をデータに保存した。
同じ文言しか正解と認める方式にせず、論理と任意性を人が採点する。
このCLIは証明を自動合格にしない。64文字で切れていても手動確認待ちとして残るため、
実装時の全文保持テストと人の採点の両方が必要。

実機用へ進める時は、紙面だけをB5/A4へ組み、音声だけを独立した読み上げ台本として使う。
expectedを撮影する用紙や読み上げへ混ぜない。
画像/録音は別の測定保存先へ置き、ケースID、実際の撮影順・発話時刻・版・hashを結ぶ。
nullのimage_file/audio_fileは未作成を示す。文字起こしの存在を実ASR成功と扱わない。

## 6. 端末なしで使う検査

リポジトリのルートで実行する。新しいCLIは外部通信・AI・端末操作を行わない。

~~~powershell
py -3.12 scripts/eval_fast_scan.py
py -3.12 -m pytest -q tests/test_fast_scan_pack.py tests/test_documentation_contract.py
ruff check .
git diff --check
~~~

答案の形式ごとの評価は、同じCLIで別のパックを読む。

~~~powershell
py -3.12 scripts/eval_fast_scan.py --pack tests/fixtures/answer_forms/cases.json
~~~

- `kind` は `rokid-answer-form-eval-v1`。小問ごとに `form`（choice / multi_field /
  worked_steps / proof / word_limit / english_composition / audio_dependent / figure）と
  `source`（試験・年度・大問・小問・欄ID・本文の由来）を持つ。
- ケースは `usage` で `tuning` と `holdout` に分かれ、`by_usage_results` で別々に集計する。
  未使用側の一致率を調整用と平均しない。
- 記述式は `manual_rubric` のみ。`rubric_origin` は人が確認済みの
  `human_checked_requirements` か、未確認の `drafted_pending_review` に限る。
  公表された出題意図や公式解答を採点基準として転記しない。
- 8形式のいずれかにケースが無い、欄IDの重複、音声なしのaudio_dependentはエラーになる。
- 本文は合成。`text_origin` に `synthetic` か `paraphrased` 以外を書けない。

供給された結果を照合する時のJSON形式:

~~~json
{
  "pack_revision": 1,
  "results": [
    {"case_id": "N01", "question_id": "Q1", "status": "answered", "answer": "36 cm²"},
    {"case_id": "L06", "question_id": "Q1", "status": "needs_material", "answer": ""}
  ]
}
~~~

上は形式の例であり、実AIの実績ではない。ローカルファイルとして保存した場合:

~~~powershell
py -3.12 scripts/eval_fast_scan.py --results C:\path\to\results.json
~~~

- 未提出の問題を分母から除外しない。客観照合17項目は、解答と材料不足判定の両方を含む。
- objective_match_rateは合成ケースの契約一致率。実資料に対するAIの正答率とは別。
- 証明1問はmanual_review。manual_review_pendingを残し、自動的に満点へ数えない。
- 数字の包含一致は禁止。例: 正解4に対する40を正解にしない。単位・否定も正規化で消さない。
- 表記揺れはaccepted_answersへ明示して追加する。rubricを変更する時はpack_revisionを上げる。
- 不明な問題ID、重複結果、旧revision、材料不足なのに答えが入った結果はエラーにする。
- 結果提供元の真正性は検証していないためsupplied_unverifiedと出す。ケース確認だけでAI実行済みにならない。
- 今回のCLIは入力整合と照合用。AIプロバイダの実行器と実機メディアの評価器は後続作業。

## 8. M0実機試験の用意

試験用PCは開発・観測にのみ使える。アプリの処理がPC/自前サーバへ依存してはならない。
USB接続・充電・画面点灯は背景動作や熱の条件を変えるため、接続有無を記録する。
最終的なスマホ操作0回の確認は、常時USBデバッグや画面点灯を成功条件にしない。

| 試験 | まず答える問い | 最小入力・観察 | 次へ進む条件 | 失敗時の分岐 |
|---|---|---|---|---|
| P03 / FS-03 | 低解像度解析・JPEG・録音が同居するか | 5分の既知音源とJPEG20回。サンプル連続性、メモリ、capture時刻、LED目視 | 正常時の無断停止なし。対応format/streamと失敗条件が分かる | カメラ構成/負荷を減らす。マイク経路を1つずつ比較 |
| P04 / FS-04 | Wi-Fiなしで任意データを双方向に運べるか | 小要求→32/64KiB程度のブロック→JPEG→音声→同時転送。原本とのhash一致 | 対応するワイヤ形式、帯域、最大payload、再送が測れる | 小通信失敗ならまずプロトコル/セッションを直す。帯域不足なら画質を保てる容量へ |
| P05 / FS-05 | スマホをロックして再利用できるか | Hi Rokid背景化、30分受信、グラス閉開、サービス再作成、翌日トークン更新 | 初期設定後にスマホを開く作業なしで再接続・結果返却 | 起動条件/省電力/認証を分けて診断。普通のBG killと明示force-stopを分ける |
| P06 / FS-06 | モバイル回線の音声認識が実用的か | L02/L03/L07を含む1分/10分音源。数字・否定・最後の発話、上りMB、遅延 | 空文字成功をせず、時刻/認識/費用/処理時間を記録できる | codec・窓の境界・前後文脈を比較。ローカルASRも候補 |
| P07 / FS-07 | 紙面と音声を両方使って解くか | L01A/B、L04、N04。画像だけ/音声だけ/両方の対照 | 正しい問題IDと全文の結果がグラスへ返る。短い統合経路が成立 | 画像・音声・対応・モデルのどこで失敗したか分ける |

初回の準備項目:
- 対象APKの版/sha256、Android/Hi Rokid/グラスfirmware/CXRの版、スマホ機種を記録。
- グラスWi-Fi未接続、スマホWi-Fiオフ、4G/5Gの接続、Bluetoothを別々に確認。
- カメラ/マイク/近距離通信/背景実行の権限と、つる開状態を確認。
- AIサービスの初期登録、採用モデル、署名付きAPKの認証、外部送信先、利用枠を設定。
- 音源と用紙のケースIDを合わせ、正解表が入力へ混ざらないようにする。

## 9. 転送予算の試算

例として音声4kB/s、実効転送帯域の20%を余裕として残し、6秒ごとに撮影すると仮定する。
画像の平均上限は (0.8×帯域−4kB/s)×6秒。
数値はSI単位の設計例で、Bluetoothの実測値ではない。

| 測れた帯域を仮定 | 6秒周期の画像サイズ上限 | 6MB画像1枚を送る最小時間 |
|---|---|---|
| 64 kB/s | 0.283 MB | 127.1 秒 |
| 128 kB/s | 0.590 MB | 61.0 秒 |
| 256 kB/s | 1.205 MB | 29.9 秒 |
| 512 kB/s | 2.434 MB | 14.8 秒 |
| 1000 kB/s | 4.776 MB | 7.5 秒 |

- 連続PCMを16kHz・16bit・monoで保存する仮定なら32kB/s、30分で57.6MB。
- 送信音声4kB/sなら30分で7.2MB。この圧縮設定で重要語を保てるかは実機評価。
- 高解像度が必要なページを落とすことで帯域を合わせない。必要領域の追加送信や
  平均サイズの調整でも要求を満たせなければ、その条件の待ち時間を正しく報告する。
- queue bytes、最古の未送信時間、音声用予約量を管理し、キュー上限で未送信を自動削除しない。

時刻は機器ごとに測る。グラスの撮影周期・終了から解答表示まで、
スマホのAI送信開始から応答までをそれぞれ同じ単調時計で測る。
端末間の時刻を比較する場合だけ、同期方法と誤差を添える。壁時計の一致を前提にしない。

## 10. 便利さの追加案と優先度

| 案 | 優先度 | 採用基準 |
|---|---|---|
| 足りない辺・少し離す等の短い誘導 | P0/P1 | 自動撮影に至らない理由が一目で分かる |
| 録音の健全性と撮影枚数を小さく表示 | P1 | RECだけの誤安心を減らし、答え表示の邪魔をしない |
| 直前の確定ページの取り直し | P1 | 3秒を過ぎた誤りをスマホなしで修正できる |
| 解析前にページ数と録音終了を確認できる短い表示 | P1 | 通常経路に追加の確認タップを要求しない |
| 字の大きさを変えても現在位置を保持 | P1 | 全文と問題位置を失わない |
| 音声の目印、撮影への復帰、明示的な追加録音 | P2 | 基本の2段階終了を複雑にせず、録音区間を区別できる |
| 失敗した問題だけ再解析、直近履歴 | P2 | 新規開始の短い導線とCLOSEDの意味を維持 |
| 非APIの音声認識/標準AI連携 | 比較候補 | 実入力・結果返却・利用条件と品質を満たす場合のみ採用 |

優先して実装するのは、自動撮影、同時録音、二段階終了、両入力解答、全文表示、
終了後の初期画面復帰とその復旧である。追加案を理由にこれらを後回しにしない。
