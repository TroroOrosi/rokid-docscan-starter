# Explain sessions

Status: Current HTTP/API guide. APP `0.16.0`, API `1.15.0`, Glasses View
contract `1.9.0`.

Explain sessions operate on pages already registered on the server. They do not
request another camera image. The HUD is output-only in the supported relay;
stage, page, and close actions come from the phone.

## Flow

1. Create a session for a finalized document with
   `POST /v1/explain-sessions`.
2. Fetch the current explanation with
   `GET /v1/explain-sessions/{id}/explain`.
3. Pass `stage=overview|detail|evidence` and `view_page=N` from phone controls.
4. Move the document page with the session next/previous-page endpoints.
5. Render the returned `glasses_view.lines`; each view contains at most three
   logical lines.

The returned navigation metadata uses `"phone"` for every operation. The
diagnostic KeyCode map in `GET /v1/settings.input` has
`operator_actions_enabled:false` and must not be interpreted as a control map.

## Response contract

A successful explanation includes the selected stage, view-page indexes,
current document-page indexes, a `glasses_view`, provider metadata, confidence,
and version fields. The view remains static: no sound, blink, animation, white
flash, or camera request is generated by this feature.

Evidence should use document-qualified, one-based references such as
`D7:P03`. Legacy `evidence_pages` remains an API compatibility field; new
consumers should use `evidence_refs`.

## Failure and privacy behavior

- A missing/unfinalized document or invalid stage/page returns a clear HTTP
  error and does not advance state.
- In `ROKID_REAL_MODE=1`, an unavailable selected real provider fails instead
  of silently returning a local placeholder.
- API keys, page text, images, provider credentials, and authorization tokens
  must not be logged.
- `camera_requests_during_review:false` means the application issues no camera
  request. Physical indicator-off remains an acceptance observation, not an
  inference from this response.
