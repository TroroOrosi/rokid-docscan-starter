# 欠陥一覧と直す順序

Status: 現行の作業台帳（2026-11-13 作成）。glassdoc 0.43.16／firmware `1.29.013-20261110-150201`／commit `d5fd31f` 時点。
ここに載せた欠陥は、この文書の「状態」が「確認済み」になるまで未解決として扱う。

## なぜ作ったか

2026-11-13 の本人の指摘（要旨）：消灯が2回目以降効かない。高画質で撮る方法も暗さ対策もない。全体の構造に欠陥が多い。
場当たりの修正が積み重なっている。言われた欠陥以外を自分で調べていない。計画的に全体を見ていない。

それまでの進め方は、指摘された一点を直し、自作の検査（注入キー・1回だけ・机上）が通れば完了としていた。
この台帳は、製品全体を独立の4系統で調べた結果（コードの読み取り）と、実機で再現した結果を、**原因の層**ごとにまとめる。
修正は層ごとに行い、症状ごとの継ぎ足しをしない。

根拠の種類：**実機**＝グラスで再現（入力はタッチパッドの入力デバイスへ直接書き込み＝実際のタッチと同じ経路）。
**読取**＝コードを読んだ結果で未実行。**推定**＝読取からの推論。

## 順序

0. 層0（システム全体の観測を先に取り、他の要素の影響を数値で把握する。以後の変更の前後でも取る）。
1. 層1（本人が最初に挙げた症状。実機で原因確定済み）。
2. 層4-1、4-4、4-5（以後の修正を、使われる条件で確かめるための土台）。
3. 層2（2-1、2-2、2-3、2-5 を一つの設計で。次に 2-4 と 2-6）。
4. 層3（3-1、3-2 から）。

各層は、失敗する試験を先に書く → 直す → 実際の入力経路と繰り返しで実機確認 → この表の状態を更新、の順で進める。
装着しての確認は、ここに「確認済み」が並び、1回で判定できる記録の準備ができてから。

Runs on: 調査と単体試験は開発用PC。実機確認はグラス＋スマホ＋PCのadb（開発時の検査で、会場の構成ではない）。
