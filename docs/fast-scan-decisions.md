# 自動スキャン・同時リスニング：確定した撮影方式

Status: 撮影方式の決定記録。**決定済み・未実装。** 2026-09-14 に圧縮、2026-09-15 に格上げ。

**本番の撮影方式はこれである**（利用者、2026-09-15）。下の R2〜R6 が方式の定義であり、
グラスが自動でページを撮り、実画像を3秒見せ、無操作なら確定して次へ進み、
ダブルタップで撮影を終える。スマホ操作は0回。

**まだ実装されていない。** コードに自動スキャンも同時録音も無い
（`AudioRecord` の実装は 0 件、`DocScanController.startAutoCapture()` は
`"Automatic capture is disabled; use explicit phone controls"` を返すだけ）。
現在の実装はページごとに1ジェスチャである。**決定と実装は別**であり、
この文書は決定の側を書いている。

2026-09-12 の解答経路改訂で優先順位が解答側へ移り、この方式は一度「保留」と
書かれていた。保留にしたのは着手順であって、方式の採否ではない。
解答経路は `ROKID_SOLVER=chatgpt-web` で確定しており、撮影方式とは独立である。

圧縮前は準備ノート（395 行）と外部アプリ参照例（99 行）の 2 本だった。残したのは**再調査の
コストが高い採否判断だけ**で、30 の運用シナリオ、M0 探針ワークシート、device-free
チェック様式、未着手タスク一覧は削除した。再開するときは、ここの判断を出発点にして
シナリオを書き直すこと。古いシナリオを掘り返すより速い。

すべて**未実行**である。設計判断であって、実機・実モデルの受け入れ結果ではない。

## 固定したユーザー要求

**固定するユーザー要求:** 撮影後の実画像を実際に3秒表示し、確認中の単タップで取り直す。
リスニングの第1ダブルタップは撮影だけを終了し、異なる第2ダブルタップで録音を終了する。
初回準備後はスマホ操作0回、グラスWi-Fiなし、スマホのモバイル回線で完走する。
これらは他アプリから導いた数値・操作ではない。他社のボタン、タイマ、クラウド前提で緩和しない。

## 見直しで判明した点（D01-D15）

| ID | 問題・根拠 | 今回の決定/着手時の対応 |
|---|---|---|
| D01 | 撮影終了待ち、録音終了、取り直しが重なると、1本の画面状態だけでは録音を誤再開しやすい | capture phase、audio phase、completionを別々に保持。録音終了後の取り直しでもマイクを勝手に再開しない |
| D02 | ページ入力/録音の最終化と「解析中」の表示が同時ではない | 資料と音声の終了manifest・欠番・最終版が揃うまで最終解答へ進めない。先行OCR/ASRと完成解答を区別 |
| D03 | 資料内の問番号は重複・再開する | 安定したquestion IDと表示上の問番号を分ける。章、資料ID、小問を保持する |
| D04 | 従来eval_exam.pyはprimary_questionの単一問題・音声なし。正解照合は文字列の包含も許す | この評価を新しい両入力の品質実績へ流用しない。新CLIは完全一致と明示した別表記だけを照合。証明は人手採点 |
| D05 | FS-27は通常モードの最初の結合点だが、後続FS-38が段階的解答の閲覧を実装する | FS-27は完成済みの通常結果を最小レイアウトで読む。FS-38は到着順不同・未完了混在・閲覧位置保持を追加 |
| D06 | M0の実機待ちをすべての机上作業の待ち条件にすると準備が止まる | データ、契約、時計注入、純粋ロジック、fake backendの準備は先に進められる。実SDKの採用決定はM0まで保留 |
| D07 | DocScanApiはJSONObjectとlong IDを返し、Controllerもその前提を持つ | UUIDをgetLongへ流さない。新モデルと旧HTTP IDの対応をアダプタで保持。JSONObjectを新しい純粋状態の保存形式にしない |
| D08 | :relaycoreはAndroid libraryで、純Javaモジュールそのものではない | 状態・期限・版の計算はAndroid SDKを呼ばない型で試験。保存/描画は境界を分け、必要箇所はinstrumentationへ |
| D09 | 音声と紙面の関係は撮影時刻だけでは決まらない。端末の単調時計にも共通の原点はない | 問題内容と全体文脈で対応する。録音サンプル位置はグラスの同一boot内で扱う。異なる端末の時刻を直接引き算しない |
| D10 | 3秒の表示要求ACKは、物理的に3秒見えた証明ではない | generation/画像ID/可視性とフレーム通知を照合。描画遅延・非可視・期限直前操作を試験 |
| D11 | モバイル通信が速くてもBluetoothの画像待ち行列は解消しない | §9の帯域式で入力の増加率を確認。圧縮・解像度・再送単位は品質と一緒に評価 |
| D12 | 取り直し後に古いAI応答が来る、閲覧終了後に残りの答えが来る | session/入力digest/結果版/閉鎖状態を照合し、古い答えで画面を開き直さない |
| D13 | 新しい1枚を取り直す操作と、以前確定したページを置き換える操作では復旧規則が違う | 新規未確定版は送信禁止。確定版の置換は新しい版が保存成功するまで旧版を保全。変更後は影響する解答を無効化 |
| D14 | グラスを折る、スマホがforce-stopされる等では、サービスを追加しただけで復帰を保証できない | 起動・切断・プロセス死を分け、前提状態を試験票に残す。M0が不成立ならスマホ操作0回を達成済みにしない |
| D15 | 期限内に触れていても、イベントが確定処理後に届く場合がある | 期限前の未決着入力を優先。確定後の遅延入力は取得時刻と表示履歴から元のページに結び、新改訂で旧解答を無効化する。無制限の入力待ちや、送信済みなのに未送信という説明はしない |
